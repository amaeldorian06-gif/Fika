## Accès au dashboard

**URL : `https://VOTRE-DOMAINE/#/admin`**

Dans l'aperçu, ouvrir le site puis **« Espace équipe »** dans le pied de page.
Le serveur accepte aussi `/admin` et redirige vers l'URL à hash.
Se connecter avec `ADMIN_EMAIL` et le mot de passe correspondant au hash du compte
Prisma `AdminUser`. Aucun mot de passe par défaut n'est désormais fourni.

Le compte doit être créé sur une base configurée. Les commandes et la procédure
de renouvellement sont dans le [README](../README.md).

## Constats prioritaires et corrections

| Constat initial | Intervention |
|---|---|
| Serveur Drizzle, logique métier Prisma non raccordée, schémas différents | Serveur unifié sur Prisma, DTO de lecture alignés sur les composants admin |
| API admin actives sans contrôle de session | Garde serveur sur toutes les routes `/api/admin` et sur la création d'avis |
| Login sans cookie, `/api/auth/me` absent | Cookie signé httpOnly, vérification du compte actif, restauration de session et déconnexion raccordées |
| Erreur serveur/validation remplacée par des données de démonstration et de faux succès | Replis retirés des clients admin et analytics ; erreurs visibles, bouton de nouvelle tentative, retour à la connexion sur 401 |
| Formulaire, événements, mutations et preuves non raccordés au serveur | Adaptation Express des fonctions métier existantes : demandes, conversions, devis, coûts, affectation, tâches, livraison, experts, avis, portfolio, analytics |
| CA/marges et compteurs partiellement fictifs ou incompatibles avec l'UI | Agrégats Prisma utilisant les fonctions métier ; coûts réels et DTO explicites |
| Secrets dans `.env.example` et le seed admin | Valeurs retirées ; seed sans mot de passe par défaut, hash obligatoire en production, commande explicite de renouvellement |
| Installation npm non reproductible | `package-lock.json` synchronisé avec le manifeste ; scripts Prisma, tests et vérification de types ajoutés |
| Schéma Prisma invalide et erreurs serveur masquées par le périmètre TypeScript | Commentaires Prisma corrigés ; serveur/seeds inclus dans le typecheck ; erreurs de typage/syntaxe corrigées |
| Documentation Next/Vercel ne correspondant pas au runtime | Guide réel Node + PostgreSQL, accès `/#/admin`, limites d'un hébergement statique documentées |

Autres protections : erreurs API JSON (pas le HTML de la SPA), corps JSON limité
à 32 Ko, refus des formulaires non JSON et des mutations explicitement cross-site,
absence de cache sur les API, bundle serveur non servi comme fichier statique.

## Connexions et travaux restant à finaliser

### P0 — Avant réutilisation de secrets ou ouverture publique

1. **Renouveler les secrets exposés** chez l'hébergeur : mot de passe PostgreSQL,
   mot de passe admin, `AUTH_SECRET`. Leur suppression du code ne les efface pas
   de Git. Changer le secret de session invalide les anciens cookies.
2. **Valider la base réelle** : connexion, migrations et compte admin. Si des
   tables Drizzle contiennent de vraies données, sauvegarder puis préparer leur
   transfert vers Prisma. Aucun transfert automatique n'a été réalisé ici.

### P1 — Cohérence opérationnelle

- **Paiements** : aucun connecteur MTN MoMo / Orange Money et pas encore de
  formulaire admin pour enregistrer/confirmer un paiement. Les transitions qui
  exigent un paiement restent bloquées tant qu'il n'existe pas. Ajouter un flux
  traçable (montant, méthode, référence, acteur), puis seulement un prestataire
  externe avec webhooks signés et idempotents si nécessaire.
- **Experts** : les routes de création/modification sont raccordées, mais l'écran
  liste n'offre pas encore le formulaire complet d'ajout/édition. À ajouter pour
  ne pas dépendre d'opérations techniques sur la base.
- **Conversion d'une demande sans téléphone** : l'API exige un numéro lors de la
  conversion ; l'interface doit encore offrir sa saisie plutôt que seulement
  montrer le refus métier.
- **Concurrence et idempotence** : numérotation devis/commandes basée sur un
  comptage et conversion de lead en plusieurs écritures. Durcir en transactions
  et séquences/réessais contrôlés avant un usage concurrent important.
- **Vraie recette de bout en bout** : demande → conversion → devis → paiement →
  expert → livraison → commande terminée → avis/portfolio. Les tests ci-dessous
  ne remplacent pas une recette sur PostgreSQL avec les données de l'équipe.

### P2 — Nettoyage et exploitation

- Le catalogue public reste statique ; le seed aligne les IDs. Prévoir une API
  catalogue seulement si l'équipe veut modifier services/prix depuis l'admin.
- WhatsApp reste un lien `wa.me` et des événements de clic, pas une synchronisation
  des messages ni une création automatique de commandes. WhatsApp Business API
  n'est utile que si cette automatisation est réellement souhaitée.
- Retirer après validation de reprise les vestiges Drizzle, les anciens scripts
  `update-server*.ts`, Firebase inutilisé et le lockfile Bun non aligné. **Utiliser
  npm comme procédure documentée**, pas ces anciens scripts.
- Ajouter une gestion de sessions révocables individuellement et des permissions
  par rôle si nécessaire. Aujourd'hui les rôles actifs partagent les opérations ;
  les cookies signés expirent après 12 h et la révocation globale passe par le secret.
- Rate limiting distribué (Redis ou proxy), purge des compteurs mémoire, pagination
  et agrégats SQL pour éviter les lectures complètes en croissance.
- Finaliser les headers du proxy Node, le domaine SEO/sitemap, les sauvegardes et
  la surveillance DB. `APP_URL` seul ne change pas les métadonnées du site actuel.
- Optimiser le bundle principal : environ 637 Ko minifié / 194 Ko gzip, avec
  avertissement Vite au-delà de 500 Ko. Le back-office est déjà chargé séparément.

## Vérifications effectuées

- **117 tests réussis**, dont 15 nouveaux tests de raccordement/authentification
  et d'absence de faux replis ; les tests HTTP utilisent un double de Prisma.
- **TypeScript : OK**, désormais sur le frontend, le serveur et les seeds.
- **Build frontend + serveur : OK**, avec avertissement de taille du bundle.
- **Lockfile npm : cohérence vérifiée** par `npm ci --dry-run --ignore-scripts`.
- **Aperçu Node : OK** — accueil 200, `/admin` → 302 vers `/#/admin`, `/api/auth/me`
  anonyme → 401, hôte de prévisualisation accepté.
- **Schéma Prisma : génération typée réussie sans moteur** après correction.
  L'installation normale du moteur a échoué : le téléchargement depuis
  `binaries.prisma.sh` est bloqué dans cet environnement. Le client sans moteur
  a servi uniquement à compiler et tester avec un double de base ; il ne valide
  pas une connexion PostgreSQL et n'est pas une procédure de déploiement.

**Non effectué :** accès à une base réelle, migrations/seed sur une base réelle,
rotation chez l'hébergeur, déploiement production, recette navigateur authentifiée,
audit de sécurité exhaustif ou audit complet des dépendances.

## Conclusion

Le raccordement applicatif est désormais cohérent et les échecs ne sont plus
masqués. L'écran de connexion est accessible dans l'aperçu. **Un dashboard connecté
aux données réelles nécessite encore la configuration et la validation de la base,
la création du compte et la rotation des secrets.** La chaîne de paiement et les
formulaires opérationnels manquants sont les prochaines intégrations prioritaires.
